# Resolute Banyan rollout and verification

[Issue #378](https://github.com/Bibleberry/Bibleberry/issues/378) · General Administration

This plan covers adoption of the permanent [PR review status policy](../pr-review-status.md), [Codename Registry](../codename-registry.md) and [handoff checkpoint](../handoff-standard.md#46-verification-checkpoint). Begin operational rollout after Aaron authorizes it. Record adoption evidence on the originating Issue and in the supporting-repository PRs. Event-driven invalidation requires separate approval.

## Manual adoption

1. **Inventory repositories and access.** Admin refreshes the organization inventory. The GitHub connector returned Bibleberry, BerryMark and Pathways as active repositories. For each repository, capture a read-only snapshot of label names, colors and IDs, the paginated list of open PRs including Drafts, unrelated PR labels, and readable effective protections and required checks. Identify in-use review-label variants on Issues and PRs. Confirm operator access and the responsible independent classifier before writes.
2. **Pilot in Bibleberry, then adopt in BerryMark and Pathways.** Create missing canonical labels in **Issues → Labels** or through the repository labels API. Correct the color of an existing exact-name label in place. Compare the five exact names and six-digit colors with the canonical policy on readback. Preserve unrelated labels and refer in-use naming conflicts to Admin before renaming labels.
3. **Backfill and reconcile.** The independent classifier checks the live HEAD, Draft state, formal disposition, hosted checks, compatibility, blockers and owner authorization on each open PR. Remove unsupported ready status first, apply the supported label and remove other review-status labels by name. Read back the complete label set and HEAD. If a write partly fails or the HEAD advances, report the observed state and reconcile from fresh evidence. Preserve unrelated labels and historical closed records.
4. **Adopt by reference.** Add links to the permanent policy, registry and handoff checkpoint on accepted Bibleberry `main` from each supporting repository's contributor or governance entry point. Document local protected branches, applicable checks and contacts there. Onboard future repositories using these same inventory, linking and verification steps.
5. **Report acceptance.** Admin verifies every repository has the five definitions and every open PR has exactly one canonical status. Compare unrelated labels with the inventory and investigate differences. Review verifies every ready PR against live same-candidate evidence and samples the other represented statuses. Use a tabletop check or separately authorized fixtures for changed HEAD, Draft correction, reopening, missing or conflicting labels, and denied access. Confirm successors can independently reproduce the pilot handoff checkpoints. Record evidence links, time, exceptions, and the next responsible party per repository.

## Optional synchronization-event invalidation

Use manual invalidation and live re-verification during the pilot. If stale ready labels routinely persist, evaluate a metadata-only handler for the `pull_request` `synchronize` event. An existing trusted GitHub App webhook may avoid Actions runners. A trusted default-branch `pull_request_target` workflow is another option. Check delivery and recovery for fork, bot, conflicting, rapid and out-of-order updates. This handler stays outside required GitHub checks and uses trusted logic with narrowly scoped label access. It never checks out or runs PR content. [GitHub webhook events](https://docs.github.com/en/webhooks/webhook-events-and-payloads#pull_request) · [GitHub Actions event behavior](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target)

Re-read the live open PR. Remove only ready status if the current candidate lacks the corresponding readiness record. A delayed event leaves valid current-candidate readiness in place. Serialize handling per PR and read back after mutation. If a race clears freshly verified status or a delivery fails, Review reconciles the result and restores readiness only after current verification. The handler never grants readiness or updates Draft state, merge or queue state, identity or protections.

## Access and rollout status

The connector reports repository admin access for the linked account in all three current repositories. Its available tools cover assigning or removing individual PR labels. Repository label definitions and effective protections could not be verified through the connector, and the local GitHub CLI could not reach the API during the inventory. Supported fine-grained credentials for repository label creation require Issues write or Pull requests write. [GitHub label permissions](https://docs.github.com/en/rest/issues/labels#create-a-label)

Approval of the documentation permits review of this PR. Operational label changes, supporting-repository changes, workflow activation and any branch protection work follow their own authorization.
