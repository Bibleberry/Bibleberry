**Audit snapshot:** `main` at `1eacda5c90ac97734b34ea08f4b8abf02098c9bf` (2026-11-19). This is a static audit of workflow definitions, package scripts, test files and scope logic. The trigger matrix includes the later Silver Badger and Pine Relay changes. The test inventory uses the audit snapshot unless a later update is named. [Claude Says #367](https://github.com/Bibleberry/Bibleberry/issues/367) (2026-11-27) updated the rows it wired into CI; see [its section](#claude-says-367-browser-release-and-toolchain-coverage). ## Executive summary

- The main verification workflows are [Bibleberry CI](https://github.com/Bibleberry/Bibleberry/actions/workflows/ci.yml), [Collections Browser Tests](https://github.com/Bibleberry/Bibleberry/actions/workflows/collections-browser.yml), [Native Android debug build](https://github.com/Bibleberry/Bibleberry/actions/workflows/native-android.yml), and [Native iOS simulator build](https://github.com/Bibleberry/Bibleberry/actions/workflows/native-ios.yml). [Merge Queue Batch Coordinator](https://github.com/Bibleberry/Bibleberry/actions/workflows/merge-queue-batch.yml) is operational automation, not a test workflow.
- Draft PRs run relevant checks. Ready promotion restarts CI, Collections and Android. iOS runs on open, reopen and synchronize, and reports evidence for the exact commit it tested.
- A Ready PR and `merge_group` run the directly wired web checks: CI scope tests, shelf persistence, Library-to-Shelf model/browser tests, lint, build, staging Worker dry-run, seven-pass reader smoke, CMS adapter/participation, gateway core, Studio validation/build, and the saved-scripture/notebook browser suites. `merge_group` forces all CI scopes to run. Android also builds/tests on a merge group. iOS does not run on `merge_group`.
- `push` to `main` runs all CI scopes and full iOS runtime acceptance. Android runs when its path filters match. Collections Browser has no `push` trigger, so those browser suites have no post-merge main run from that workflow. Since Claude Says (#367), every checked-in `tests/**/playwright.config.ts`, the performance suite and the R06 release artifact build are invoked by `ci.yml`; database-gated suites remain outside hosted CI.
- `workflow_dispatch` exists only for the merge-queue coordinator and the native workflows. Manual Android dispatch runs its build. Manual iOS dispatch runs build and runtime acceptance with an opt-in lifecycle probe. There is no manual dispatch for CI or Collections.
- Workflow test jobs use read-only repository contents permissions, ephemeral GitHub-hosted runners (`ubuntu-24.04`, `macos-26`), and test fixtures/harnesses in-tree. Database acceptance uses local Supabase/Postgres/Docker and is not part of the normal hosted test jobs. Never treat the latter or physical-device acceptance as satisfied by these checks.

### Indirect checks and non-coverage

`npm run lint`, `npm run build`, Studio `typecheck`/`build`, the staging `wrangler deploy --dry-run`, and Android/iOS compile steps may parse, type-check, bundle or package source files. They do not execute the behavioral tests above. Similarly, fixture imports in a test do not mean every feature test using a related module ran. `test:performance` is present in `package.json` but no workflow invokes it. No workflow in this matrix proves production Supabase behavior, private Sanity publication, release content approval, real account privacy/deletion, or physical iOS/Android device acceptance.

## Scope rules, fixture security, and false-green risks

`scripts/ci/check-scope.mjs` defines universal triggers: `.github/**`, root `package.json`/lockfile, ESLint config, `scripts/ci/**`, and `tests/ci/**`. For PRs it reads the complete merge-base diff against `main`, failing open (run=true) when the diff cannot be determined. A missing/empty diff is treated as no matching changes. `merge_group`, `push`, and manual calls always run. Target rules also make all `tests/**` changes run the reader job; relevant Studio, gateway, or browser code runs their corresponding jobs.

The key false-green gap at the audit snapshot was that target scope and invoked test command were different sets. Collections scope included `tests/cardViewer/**` and `tests/announcements/**` while its command invoked only the saved Scripture and Notebook specs; its registry and parity test have since closed that gap. A change to `tests/savedScripture/savedScriptureCollectionModel.test.ts` also triggers both reader and Collections jobs, but neither command invokes that hermetic Node model suite. Conversely, broad reader test scope causes the reader job to run for every test edit, but `test:smoke` invokes only the seven pass list. Thus job success does not mean all changed test files executed. There is no CI workflow-level path filter on `ci.yml`; subsystem scope skips are visible as successful jobs with an explicit skipped step. Android uses workflow-level path filters on PRs and main pushes. iOS reports a scoped skip in the workflow summary when appropriate and always runs full acceptance on main pushes.

Fixture policy for the current automated tests: use checked-in synthetic fixtures and local harnesses; do not include account credentials, private service tokens, live reader identities or non-public editorial exports. The account DB/Supabase suites intentionally require isolated local services and their own setup. Do not run them against shared or production endpoints. Workflow permissions declare `contents: read`; write-capable merge coordinator workflows are separate from test workflows.

## Claude Says (#367) browser, release and toolchain coverage

[Issue #367](https://github.com/Bibleberry/Bibleberry/issues/367) repaired two failing browser suites, made the Month Screen accessibility suites self-starting and wired the remaining hermetic suites into `ci.yml`. [CI policy guard](../../tests/ci/ci-coverage-repair.test.ts)

- **R06 Library landing (`tests/r06Library`).** Root cause: stale test, not a product regression. Since [Saffron Ledger #351](https://github.com/Bibleberry/Bibleberry/pull/351) the R06 Shelf card takes its title and completion progress from the gateway Month lookup, and it withholds the title when that lookup is unavailable or withdrawn. `tests/readerShell/month-shelf.spec.ts` asserts that fail-closed behavior. The harness never answered the lookup, so it now supplies a synthetic Month provider. The origin/authorization test also expected Add and Open buttons for current and future months. [Willow Quay #347](https://github.com/Bibleberry/Bibleberry/pull/347) withholds those months from the Library entirely and updated the equivalent `tests/libraryShelf` assertion, but not this one. It now asserts the months are absent.
- **Hub Continue Harbor Signal G04-A (`tests/hubContinue`).** Root cause: test defect present since it was introduced in #273, not a product regression. Step 3 finishes Day 1, so Hub Continue has nothing to resume and shows the Active Focus Month (`openFocusMonth`). That card offers only the primary `Continue Your Study` Month entrance. The secondary `View <Month>` action exists only on resume suggestions, so step 4 waited for a control that state never renders. Step 4 now uses the primary entrance and asserts the card kind. The forged-origin and reload checks are unchanged.
- **Month Screen accessibility.** `npm run test:month-accessibility` builds its own flagged bundle outside `dist/` and serves it, so it runs from a clean checkout.
- **`reader-app` hermetic step** adds `accountAuth/supabaseGoTrueProvider`, the four `accountDatabase/*Static` guards, `appIntegration/teachingScripture`, `challenge/challengeReaderControls`, `r06Library/r06LibraryModel`, `releaseAudit/monthlyPublicationAudit` and `shelfUI/shelfModel`.
- **`reader-browser-suites` job** (`Reader browser suites (Chromium)`) runs `test:performance` after Chromium setup, then the App integration, Card Sharing, Challenge, Hub Continue, Historical Library, Month Screen accessibility, News, Onboarding Replay, R06 Library, Scripture Capture and Shelf UI Playwright configs. Every `tests/**/playwright.config.ts` is now executed by a workflow, and the guard test fails if a new config is not.
- **`r06-release-artifact` job** (`Build and verify R06 release artifact`) runs `tests/release/r06-preflight.test.mjs`, builds the shipped R06 artifact with `scripts/release/r06-preflight.mjs build` at the checked-out commit, verifies it against the printed manifest digest and runs the packaged-reader `smoke`. The digests appear in the job summary. This is a CI rehearsal of the build: it does not deploy, run the Access `perimeter` check, or replace the independently recorded qualification evidence. The ordinary `Build application` step in `reader-app` still builds the legacy entry.
- **Toolchain.** `.nvmrc` pins Node 24.22.1, the recorded R06 release toolchain, for every job in `ci.yml` and `collections-browser.yml` except `sanity-studio`. Studio is a separate package with its own lockfile and stays on Node 22. Native and merge-queue workflows are unchanged. `.nvmrc` is a universal scope trigger.
- **Gateway scope.** `release-gateway` now also matches `src/cms/reader/**`, `src/cms/sanity/**` and the three fixture/acceptance scripts in the gateway tests' import graph. The guard test recomputes that graph.
- **Not changed.** The new jobs are not yet required status checks; branch-protection contexts are an owner setting. Local Supabase/Postgres/Docker suites, `perf:baseline`/`perf:compare`, native workflows and deployment remain outside hosted CI.
